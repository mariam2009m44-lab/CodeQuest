# خطة دمج Django في CodeQuest

## القرار المعماري

- الواجهة الحالية HTML/CSS/JavaScript وReact تبقى كما هي.
- FastAPI يبقى مسؤولًا عن API تشغيل الأكواد وخدمات Cody الحالية.
- Firebase Authentication وFirestore يظلان مسؤولين عن هوية الطلاب وتقدمهم ومكافآتهم.
- Django يُستخدم كخدمة إدارة داخلية للمحتوى التعليمي والإعلانات والمشاريع.
- لا تتم مزامنة محتوى Django إلى ملفات JSON أو Firestore تلقائيًا في هذه المرحلة.

## مراحل التنفيذ

1. **الأساس الإداري (موجود في هذا الفرع):** مشروع Django مستقل ونماذج للمسارات والمناهج والدروس والأسئلة والإعلانات والمشاريع.
2. **استضافة آمنة:** نشر لوحة الإدارة على خدمة Python مستقلة مع HTTPS وقاعدة بيانات PostgreSQL دائمة، وضبط الأسرار والنطاقات والنسخ الاحتياطية.
3. **تكامل المحتوى:** تصميم خدمة تصدير/نشر versioned للمحتوى إلى مصدر موحد. يجب الحفاظ على lesson IDs الحالية حتى لا تنكسر سجلات تقدم الطلاب.
4. **المراجعة والصلاحيات:** أدوار محرر ومراجع ومدير، وسجل تدقيق قبل السماح بالنشر.
5. **اختبارات التكامل:** اختبار ظهور الدروس المنشورة في الواجهة، وعدم تغيير progress IDs أو مكافآت XP/stars، والتحقق من Firestore في بيئة اختبار.
6. **التوسع:** إضافة تقارير إدارية مجمعة لا تكشف بيانات شخصية للطلاب دون حاجة أو صلاحية.

## شروط الانتقال للإنتاج

- لا تستخدم SQLite كقاعدة بيانات إنتاجية متعددة المستخدمين؛ استخدم PostgreSQL مستضافة.
- لا تجعل لوحة الإدارة متاحة للطلاب أو عامة دون مصادقة staff.
- لا تحفظ تقدم الطلاب في Django؛ تجنب إنشاء مصدرين للحقيقة.
- لا تنشر Django على GitHub Pages؛ يتطلب خادم Python.
- لا تُعلن عن اكتمال التكامل أو نشر Firebase Functions إلا بعد دليل تشغيل واختبارات موثوقة.
